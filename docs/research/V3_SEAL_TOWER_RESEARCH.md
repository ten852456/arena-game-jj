# แนวคิดต่อจาก V3: Seal, Idle Town และ Tower — โจทย์ให้เจเจค้นคว้าต่อ

วันที่: 27 พฤศจิกายน 2026  
สถานะ: **แนวคิดและคำถามเพื่อวิจัย ไม่ใช่สเปกที่ตกลงแล้วหรือฟีเจอร์ที่ทำเสร็จ**

> เอกสารนี้เป็นหัวข้อต่อจาก V3 สำหรับนำไปคุยและค้นคว้าต่อ ตำแหน่ง “tab ต่อจาก V3” ในเอกสารปลายทางยังไม่ได้ระบุ จึงจัดไว้เป็น Markdown แยกก่อน

## 1. ภาพรวมที่เจ้าของกำลังคิด

เชื่อม Auto-battler, เมือง idle และการไต่หอเข้าด้วยกันด้วย **Seal**: เล่น Auto-battler แล้วผนึกสกิลออกมาเป็นของที่นำไปใส่ให้ตัวละคร ใช้ทำงานในฟาร์มหรือใช้ไต่หอได้ และอาจขายให้ผู้เล่นอื่นได้ มีการเติบโตของระดับ การสุ่มค่า และ gimmick เช่น การกลายพันธุ์

วงจรที่อยากสำรวจ:

**เล่น Auto-battler → ผนึกสกิลเป็น Seal → ใช้ใน Farm หรือ Tower / ขาย → ได้ทรัพยากรและรางวัล → จัดฮีโร่ สกิล รูน อุปกรณ์ และ AI เพื่อเล่นต่อ**

Auto-battler อาจเป็นโหมด casual ที่เล่นได้ตามปกติ โดยพิจารณา **เอา ticket ออก** และเปลี่ยนไปคิดรางวัลจากการไต่หอ ส่วน Tower อาจเป็นระบบที่ผู้เล่นตั้งบอต/AI ให้ตัวละครเล่นตามบทบาท สกิล รูน และอุปกรณ์

**ยังต้องยืนยัน:** คำว่า casual ในที่นี้หมายถึงโหมด Arena, Tower หรือทั้งสองส่วน และ Tower จะแข่งอันดับ/ชิงรางวัลมูลค่าหรือเป็น PvE รับรางวัลส่วนตัวก่อน

## 2. Seal: ของที่สร้างจากประสบการณ์ใน run

- แนวคิดตั้งต้น: เมื่อจบ run ผู้เล่นเลือกสกิลที่ใช้ในรอบนั้นมาผนึกเป็น Seal เพื่อนำไปใช้ต่อ
- Seal มีสกิล ระดับ ค่าสุ่ม และอาจมี mutation; ผู้เล่นเลือกใช้เอง เก็บสะสม หรือขาย
- ต้องตัดสินว่า Seal ติดกับฮีโร่ประเภทใดได้บ้าง, หนึ่งตัวใส่ได้กี่ชิ้น, ใช้ใน Farm และ Tower พร้อมกันได้หรือไม่, ถอดเปลี่ยนได้เมื่อไร และขายแล้วผู้ขายเหลืออะไร
- ถ้าซื้อขายเป็นชิ้น ควรแยก **ความชำนาญติดบัญชี** ออกจาก **Seal แต่ละชิ้นที่โอนเจ้าของได้** เป็นข้อเสนอให้ศึกษา ไม่ใช่ข้อสรุป ตัวอย่าง: เล่นและผนึก Ignite บ่อยขึ้นจนปลดระดับ C; สร้าง Ignite Seal C ออกมาแล้วเลือกใช้หรือขาย โดยความชำนาญยังอยู่กับผู้สร้าง
- แยกจาก **mark/ตราใน run ปัจจุบัน** ซึ่งเป็นอีกกลไกหนึ่ง อย่าสมมติว่าเป็นสิ่งเดียวกัน

## 3. ระดับและการสุ่ม — ตัวอย่างที่เจ้าของเสนอ

ตัวอย่างแนวคิด: เริ่มระดับ **D สุ่ม 1–5**; เมื่อลงครบ 3 ครั้งเป็น **C สุ่ม 2–7** แล้วอาจมีระดับสูงขึ้นตามการเล่น ตัวเลขและหน่วยเป็นตัวอย่างเท่านั้น ยังไม่ได้ตัดสินว่าเป็นเปอร์เซ็นต์ ผลแบบใด หรือช่วงใดสมดุล

คำถามที่ต้องตัดสินก่อนออกแบบต่อ:

1. “ครบ 3 ครั้ง” นับ **ทุก run ที่เล่น**, run ที่ผ่านเงื่อนไข, การใช้สกิลนั้น หรือการเลือกผนึกสกิลนั้น? นับย้อนหลังต่อบัญชีหรือต่อชิ้น?
2. ระดับ D/C เป็นระดับความชำนาญผู้สร้าง, ระดับของ Seal แต่ละชิ้น หรือทั้งคู่? Seal ที่ซื้อจะอัปเกรดได้หรือไม่?
3. ค่าสุ่มจาก D และ C ซ้อนช่วงกัน: ถ้ามี D +5 แต่สุ่ม C ได้ +2 จะให้เก็บค่าเดิม รับชิ้นใหม่ตามผลจริง หรือมีการันตีเมื่อเลื่อนระดับ? แต่ละวิธีส่งผลต่อจำนวนของและตลาดต่างกัน
4. เปิดเผยช่วง ค่าแต่ละค่าและโอกาสอย่างไร; มี pity หรือทางสะสมเพื่อให้ความคืบหน้าแน่นอนหรือไม่?
5. คนเล่นน้อย คนแพ้บ่อย และคนเริ่มใหม่จะได้ของและรู้สึกคืบหน้าเพียงพอไหม?

ตัวอย่างก่อนหน้าที่เสนอให้เก็บค่าสูงสุดเหมาะกับสมุดถาวร แต่ **ยังใช้ตรง ๆ กับ Seal ที่ซื้อขายเป็นชิ้นไม่ได้** ต้องกำหนดว่าผลสุ่มสร้างชิ้นใหม่หรือปรับชิ้นเดิม และเกิดอะไรขึ้นเมื่อขาย

## 4. Mutation และตัวอย่างการใช้งาน

Mutation ควรพิจารณาให้เปลี่ยน **วิธีเล่น** มากกว่าทำให้ของหายากเก่งกว่าปกติทุกด้าน เพื่อให้ Seal หลายแบบมีคุณค่าและมีคนใช้จริง ตัวอย่างทั้งหมดเป็นแนวคิด ไม่ใช่ค่าสกิลที่มีอยู่:

| Seal | ตัวอย่าง Farm | ตัวอย่าง Tower |
|---|---|---|
| Ignite | เพิ่มผลผลิตไม้; mutation ทำงานช่วงต้นเร็วแต่คลังไม่ใหญ่ขึ้น | เปลี่ยนวิธีใช้สกิลไฟ หรือเพิ่มผลภายใต้เงื่อนไข |
| Shield | เพิ่มความจุคลัง | ช่วยป้องกันเพื่อนตามเงื่อนไข |
| Time | เร่งงานช่วงเวลาหนึ่ง | เปลี่ยนจังหวะใช้สกิล |
| Heal | ช่วยการฟักไข่ตามชั่วโมงทำงาน | รักษาเป้าหมายที่กำหนด |

วิจัยต่อว่า mutation ควรสุ่มเมื่อสร้างหรือปรับภายหลัง, เปลี่ยนได้หรือไม่, มี trade-off แบบไหน, มีโอกาสออกเท่าไร, ซื้อขายได้อย่างไร และจะป้องกันการไล่สุ่มแบบไม่มีที่สิ้นสุดได้อย่างไร

Farm ยังมี affinity ฮีโร่และระบบคลังในแบบเดิม ต้องจำลองว่าโบนัส Seal บวกหรือคูณกับ affinity, มีเพดานรวมเท่าไร และความเร็วที่เพิ่มขึ้นช่วยคนเข้าเก็บวันละสองครั้งจริงไหมถ้าคลังเต็มเร็วขึ้น

## 5. Tower: จัดทีมและตั้ง AI

แนวคิดของเจ้าของ: ให้ AI เล่นและให้ผู้เล่นตั้งบอตสำหรับการไต่หอตาม **role ของตัวละคร, สกิล, รูน และอุปกรณ์** ผู้เล่นจัดทีมและปรับแผนจากผลการสู้

ตัวอย่างเพื่อสำรวจ: Knight เป็น tank ใช้โล่ตามเงื่อนไข; Pyromancer ทำดาเมจ; healer เลือกเพื่อน HP ต่ำ; support ควบคุมจังหวะ ศึกษาว่าต้องใช้กี่ตัวต่อทีม, กติกาการสู้, HP และทรัพยากรข้ามชั้น, การหยุด/แก้แผน และรางวัลแต่ละช่วง

แนวทางเริ่มต้นที่เสนอ: มี AI preset ตาม role แล้วให้ผู้เล่นปรับเงื่อนไขง่าย ๆ 2–3 ข้อ เช่น “HP ต่ำกว่า 50% → ใช้ Heal” แทนการบังคับตั้งระบบบอตละเอียดตั้งแต่แรก ต้องทดสอบว่ามีการตัดสินใจพอและผู้เล่นเข้าใจเหตุผลที่แพ้หรือไม่

**รางวัลไต่หอ:** วิจัยทางเลือกของรางวัลรายชั้น, ครั้งแรก, รายวัน/ซีซัน และอันดับ รวมถึงแหล่ง/ที่ใช้ของรูน อุปกรณ์ และทรัพยากร โดยยังไม่สมมติว่ามีรางวัลเงินจริง

## 6. Ticket, ตลาด และความเป็นธรรม

เจ้าของเสนอให้พิจารณา **เอา ticket ออก** แล้วคิดรางวัลจาก Tower แทน ยังต้องตัดสินว่าเอาออกจากโหมดใดบ้าง และ Arena จะให้ Seal ได้บ่อยแค่ไหน ตัวเลือกเพื่อวิจัย:

- เล่น Arena ฟรีไม่จำกัด และให้ทุก run สร้างของขายได้: เข้าเล่นง่าย แต่เสี่ยงของล้นและหลายบัญชี/บอตผลิตของ
- เล่นฟรีไม่จำกัด แต่จำกัดสิทธิ์สร้าง Seal ที่ขายได้ตามช่วงเวลา/เงื่อนไข: รักษาโอกาสเล่น แต่ต้องระวังความรู้สึกถูกจำกัดและวิธีกันหลายบัญชี
- เล่นฟรีและรับความคืบหน้าที่ใช้เองเสมอ แต่การสร้างของขายต้องมีเงื่อนไขเพิ่มเติม: ต้องระบุความต่างและประเมินผลต่อผู้เล่นใหม่

จำนวน “3 สิทธิ์ต่อวัน” ที่เคยยกขึ้นมาเป็น **ตัวอย่างเท่านั้น** ยังไม่มีข้อมูลรองรับ ไม่ใช่ข้อสรุป และเพดานรายบัญชีอย่างเดียวไม่ป้องกันหลายบัญชี

ถ้า Seal ซื้อขายได้และมีผลต่อ Tower ต้องตอบว่า **การซื้อพลังมีผลต่อรางวัลหรืออันดับหรือไม่**:

1. Tower casual ใช้ Seal ได้เต็มที่; ความคืบหน้าสะท้อนทั้งการสะสมและการจัดทีม
2. แยกหอแข่งขันที่ปรับค่าหรือจำกัดอุปกรณ์ให้เท่าเทียมจากหอ casual
3. แข่งแบบเปิดโดยยอมรับและสื่อสารว่าของที่ซื้อส่งผลต่อผลแข่ง

ทางเลือกที่ 2 เป็นข้อเสนอเบื้องต้น ไม่ใช่มติ ควรเทียบความสนุก ประชากรผู้เล่นที่ถูกแบ่ง และความเป็นธรรมกับเป้าหมายรางวัลจริง

ต้องวิจัยเศรษฐกิจ Seal ทั้ง **แหล่งผลิต, ความต้องการใช้, การสึก/การเผาหรือวิธีนำของออกจากระบบ, ของล้นตลาด, ราคา, ค่าธรรมเนียม, การผูกบัญชี, การฉ้อโกงและบอต** รวมถึงวิธีชำระเงินจริงหรือโทเคนที่ตั้งใจใช้ ถ้ามี ตรวจข้อกฎหมาย การคุ้มครองผู้เยาว์ การสุ่ม/ซื้อขาย และกฎแพลตฟอร์มตามประเทศและรูปแบบจริงก่อนตัดสินใจ

## 7. สิ่งที่เปลี่ยนจากแบบเดิมและต้องตกลงใหม่

- [FARM.md](FARM.md) เคยวาง **ทรัพยากรผูกบัญชีและ ticket จากฟาร์ม**; ข้อเสนอใหม่อาจเอา ticket ออกและเพิ่ม Seal ที่ซื้อขายได้ ต้องตัดสินขอบเขตใหม่อย่างชัดเจน
- แบบเดิมเน้นฮีโร่ตัวเดียวกันมีพลังเท่ากันใน Arena และไม่มี paid combat power; Seal ที่ซื้อได้และมีผลต่อ Tower อาจเปลี่ยนหลักนี้ถ้า Tower มีการแข่งขัน/รางวัลที่มีมูลค่า
- แบบเดิมมี hero affinity, supply ของ Tower, monument และ pass ที่อาจส่งผลต่อการฟาร์ม ต้องตรวจผลรวมกับ Seal รวมถึงขอบเขตการซ้อนโบนัสและเพดานต่าง ๆ
- การขาย Seal เป็นแนวคิดใหม่ **ไม่ได้หมายความว่าทรัพยากรฟาร์ม ไข่ หรือทุกไอเทมขายได้** ต้องแยกการตัดสินใจแต่ละประเภท
- สกิล Arena ใน run เดิมเป็นของชั่วคราว: ต้องกำหนดว่าการผนึกอ่านสกิล/สาย/ทางอัป/เลเวล ณ เวลาใด และไม่ให้ค่าสะสมถาวรเปลี่ยนความเท่าเทียมของ Arena โดยไม่ตั้งใจ

## 8. คำถามวิจัยสำหรับเจเจ

1. เกมที่ให้ผู้เล่นสร้างของจาก run, สุ่มคุณสมบัติ และนำไปใช้หรือขาย ทำอย่างไรให้ทั้งผู้สร้าง ผู้ซื้อ และผู้เล่นใหม่ยังสนุก? หาแหล่งอ้างอิง กลไกจริง และข้อจำกัดของแต่ละตัวอย่าง
2. การเติบโต D → C → B ควรนับอะไร? ทดลองจำนวน run ต่อวัน 1/3/7 และอัตราแพ้/เจอสกิลต่างกัน เพื่อดูเวลาปลดระดับจริง
3. สุ่มค่าและ mutation แบบใดทำให้มีของหลากหลาย แต่ไม่กดดันให้ roll ซ้ำไม่สิ้นสุด? เปรียบเทียบ pity, เลือกผล, สุ่มมีเพดาน และการเก็บค่าที่ดีที่สุด โดยแยกของติดบัญชีจากของขายได้
4. จำลองจำนวน Seal ที่เข้าสู่ตลาด การถือครอง การใช้และการนำออกจากระบบ ภายใต้ free play, การจำกัดสิทธิ์, หลายบัญชี และบอต ความเสี่ยงใดแก้ด้วยระบบเกมได้ และอะไรต้องใช้มาตรการบัญชี/เศรษฐกิจ?
5. ฟาร์มและ Tower ควรใช้ Seal ชิ้นเดียวกันอย่างไร? เปรียบเทียบใส่พร้อมกันกับแย่งช่องใช้งาน รวมถึงการเรียกฮีโร่กลับจากงาน
6. Tower แบบ PvE ส่วนตัว, leaderboard และรางวัลมีมูลค่า ต้องใช้กติกา Seal/อุปกรณ์ต่างกันหรือไม่? ประเมินทั้งความยุติธรรม ความสนุกและรายได้
7. AI preset และระบบเงื่อนไขขั้นต่ำที่สร้างความสนุกคืออะไร? ทดลองกับผู้เล่นใหม่และผู้เล่นชอบปรับบิลด์ โดยดูว่าพวกเขาเข้าใจสาเหตุแพ้หรือไม่
8. หากเอา ticket ออก ทรัพยากรไม้/แร่/คริสตัลจะมีที่ใช้หมุนเวียนพอหรือไม่? จำลองรวมเมือง, Tower, monument, Seal และข้อจำกัดของ pass
9. การสุ่มของที่ซื้อขายได้ต้องตรวจประเด็นกฎหมายและ platform policy อะไรบ้างสำหรับประเทศ ผู้เล่น และช่องทางชำระเงินจริงที่ตั้งใจรองรับ?

## 9. ขอบเขตต้นแบบที่เสนอให้ประเมิน

ต้นแบบเล็กเพื่อทดสอบความสนุกก่อนสร้างระบบตลาดจริง: สกิลผนึก 5 แบบ, D/C, mutation 2–3 แบบ, ตัวละครใส่ Seal ได้ 1 ชิ้น, ฟาร์มหนึ่งจุด และ Tower ทีมเล็กพร้อม AI preset ทดสอบตลาดด้วยข้อมูลจำลองหรือกลุ่มปิดก่อน ตัวเลขและขอบเขตทั้งหมดเป็นเพียงข้อเสนอ

**ผลลัพธ์ที่อยากได้จาก research:** เปรียบเทียบทางเลือกพร้อมตัวอย่างอ้างอิง, ความเสี่ยงและข้อขัดแย้งกับแบบเดิม, แบบจำลองเศรษฐกิจ/เวลาเล่น, คำถามที่ต้องให้เจ้าของตัดสิน และข้อเสนอ MVP ที่ทดสอบได้ ไม่ต้องถือว่าข้อเสนอในเอกสารนี้ได้รับอนุมัติแล้ว
